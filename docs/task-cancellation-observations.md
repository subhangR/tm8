# Legacy task cancellation observations

Open this when changing Taskland lifetime reads, task creation clocks, or task restore/import tooling.

Migration 316 records exact status transitions with `clock_timestamp()` and preserves the timestamp on same-value status writes. Rows predating that clock can have a null timestamp. Generic task/entity `updated_at`, activity and version timestamps cannot date their cancellation: an older transaction can commit a later generic write and regress a transaction-start `now()` value.

Migration 317 runs in one READ COMMITTED transaction. It acquires SHARE ROW EXCLUSIVE on `public.tasks`, which conflicts with task writers' ROW EXCLUSIVE locks. After those writers commit or roll back, a separate statement observes all currently cancelled, exact-null tasks and records a per-task `status_changed_not_after` clock. The lock excludes new task writes until migration commit. The observation is a conservative upper bound on cancellation, never an exact cancellation date. A 5-second lock timeout aborts the whole migration safely; rerun the migration after contention clears. `db/migrate.mjs` wraps each migration and its ledger record with `psql -1`.

The bound assumes the system wall clock does not step backwards during observation, consistent with 316's wall-clock convention. It is independent of task titles, activities and version history. Same-value cancellation preserves the observation; actual transitions or exact stamps delete it. Task deletion cascades the metadata. App transactions have only SELECT access, under entity RLS.

Ordinary INSERT establishes an exact initial status clock, including a task created cancelled. A supplied timestamp is overwritten. Historical imports must run as `tm8_graph_owner`, outside app/delivery transaction roles and without authenticated identity claims, with `SET LOCAL tm8.bulk_load = 'on'`. Only that owner restore path can preserve an imported exact timestamp or NULL. A custom bulk-load GUC alone grants no exception to authenticated or app-role callers, including owner SECURITY DEFINER creation functions. Later imported NULL task IDs have no observation record and remain unknown. Tools that bypass triggers or replace existing task states must discard observation rows for replaced tasks; restore observations only with their matching uninterrupted cancellation state.

`tasks.cancellationObservations` is a read-only POST at `/v2/spaces/:spaceId/tasks/cancellation-observations`. It takes only `{taskIds: UUID[]}`, at most 500 IDs, and binds the authenticated viewer through transaction claims and `internal.is_space_member`. The result is `{schemaVersion: 'tm8.task-cancellation-observations.v1', spaceId, complete: true, facts: [{taskId, statusChangedNotAfter}]}`. Every selected readable, undeleted, currently cancelled exact-null task with captured evidence appears once. Missing facts mean unknown, ineligible or unreadable; they disclose no reason or title. Completeness covers this bounded selection, not all tasks in the space.

The cold Game loader reads only admitted cancelled exact-null tasks, in chunks of at most 500. It checks response identity and schema, ignores unrequested facts and joins `MapEntity.cancelledNotAfter` immutably. Missing, unavailable or invalid facts remain unknown. The model uses a bound plus 24 hours only as a conservative removal deadline; exact `cancelledAt` wins and `rubbleExpiresAt` remains exact-only. It never renders an observation as an actual cancellation date. Both space and story scopes are covered. Events integration owns preserving a prior proven bound across same-episode title upserts and clearing it on reopen/reset; this unit does not change the accepted projector or live controller.

Real PostgreSQL tests include reverse transaction ordering, an observed migration lock wait, observation versus the actual writer commit timestamp when commit tracking is enabled, new-task insertion clocks, same-value cancellation, reopen/re-cancel, later NULL imports, supplied stamp rejection, an app-role SECURITY DEFINER bulk-guard probe, RLS, pin/space isolation and bounded disclosure. Client tests cover both cold loaders, reload removal timers, exact precedence, immutable joins, missing/failed facts and 500-ID batching.
