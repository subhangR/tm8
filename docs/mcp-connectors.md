# MCP connector definitions

Open this document when registering, importing, attaching, or launching an MCP connector. It describes definition metadata, the authorization boundary, and CLI selection behavior. Remote credentials and OAuth implementation are described in [the credential boundary ADR](adr/0297-mcp-credential-boundary.md).

In the native UI, open the MCP catalog to register or import definitions, or choose **Browse directory** to prefill an official remote server (Notion, Slack, Figma) and add it like any other definition. Open a connector to approve it, connect an account by API key or OAuth, run a connection test, and inspect its tools. The account picker distinguishes accounts you can use from accounts you can manage. Task and teammate connector editors manage defaults; the launch picker explicitly chooses each account for that launch. Disconnect removes the selected account or attachment; revoke prevents future account use.

Any member of a space registers a `mcp_server`, and it is approved the moment it is added (migration 405: there is no approval step). Its definition contains a stable name, transport, URL or command/arguments, authentication metadata, and names of secret slots. Literal `env` or `headers` maps are rejected. The name `tm8` is reserved; names are unique within a space ignoring case. Registration, editing, deletion, stdio trust, and private-network access need only space membership, through the MCP facade and generic entity operations alike. Setting `approved: false` on an existing connector still switches it off.

HTTP definitions use one declared API-key header, OAuth, or no authentication. Stdio definitions use one declared API-key environment variable or no authentication. Executing stdio requires `stdioTrusted: true`: the executable receives its configured credential and must be trusted with it. `allowPrivateNetwork` is an explicit choice in the definition, not something inferred from a submitted URL. Keep literal credentials out of URLs, commands, arguments, provenance, and names.

For example, save this nonsecret request as `connector.json`:

```json
{
  "definition": {
    "name": "example",
    "transport": "http",
    "url": "https://example.test/mcp",
    "envKeys": [],
    "headerKeys": ["Authorization"],
    "auth": {"type": "api_key", "headerName": "Authorization", "prefix": "Bearer"},
    "approved": false
  }
}
```

Run `tm8 mcp server create --input @connector.json`. Update the complete definition with `tm8 mcp server update <server-id> --expected-version <version> --input @connector.json`. An import takes `{"definitions": [...]}` through `tm8 mcp server import --input @connectors.json`; the whole batch is transactional. That operation still refuses literal credentials; `tm8 mcp import` is what converts a native config into definitions with named slots.

## Reusing a Claude Code or Codex configuration

`tm8 mcp import --from claude|codex|mcp-json [--path <file>]` reads the MCP servers a member has already configured on their own machine and registers them as connectors. The default sources are `~/.claude.json` (the global `mcpServers` block and every `projects[*].mcpServers` block), a project `.mcp.json`, and `~/.codex/config.toml` (`[mcp_servers.*]`, including `bearer_token_env_var`, `http_headers` and `env_http_headers`). The server never reads these files: the command runs in the member's own process, and the translator (`@tm8/contract`'s `translateMcpConfigText`, shared with the UI's import box) emits metadata only.

`http`/`sse` entries become HTTP definitions at the same URL, `command`/`args` entries become stdio definitions, and a literal header or environment value becomes a declared slot with `api_key` auth — never definition content. A host tm8 knows speaks OAuth (Slack, Notion, Figma, Linear, GitHub, Atlassian, Sentry, Asana, Stripe, Intercom) and that carries no credential of its own becomes an `oauth2` definition to connect in tm8 instead. Everything the translation drops — a second header, an illegal header name, a URL carrying a query string — is reported rather than silently skipped.

A `command`, its `args` and a `url` are ordinary definition content that every space member can read, and unlike a header or environment value there is no slot to move a literal out of. So a connector whose argv or URL path carries a literal credential is **refused** with a reason rather than registered: a credential-named flag followed by a value (`--api-key sk-…`), the `=` spelling (`--token=ghp_…`), a `KEY=value` pair with a credential-named key (docker `-e SLACK_BOT_TOKEN=xoxb-…`), a known provider token shape anywhere in the argv or in a URL path segment, and any long mixed-case high-entropy argument. A shell expansion (`${ACME_KEY}`), an environment variable passed by NAME (`-e GITHUB_PERSONAL_ACCESS_TOKEN`) and ordinary paths, ports and package specifiers are left alone.

Deciding what an import registers is one shared step (`selectMcpImports`), so the CLI and the UI box behave identically: a duplicate endpoint, a local command without explicit code trust, and a row past the 32-connector ceiling are each skipped and reported, never a reason to refuse the rest of the configuration, and a name the space already uses is renamed so one clash cannot fail the transactional batch.

`--dry-run` prints the plan and writes nothing; it deduplicates against the space's connectors by URL for HTTP and by argv for stdio. `--trust-stdio` is required before any connector that runs a local command is registered. `--with-credentials` additionally seals each literal token found in the file as the importing member's own private credential through the human-only `mcp.credentials.create`; without it the token stays in the file and is only counted. Imported connectors arrive approved (405), nothing is ever shared with the space, and no token is printed. Launches are unaffected: `--strict-mcp-config` and the stripped Codex home stay exactly as ADR 0297 requires, because a connector reaches an agent only through the tm8 bridge.

A human creates a private account with `tm8 mcp credential create <server-id> --input @credential.json`. The file contains `{"label":"My account","secret":"..."}`. Use a restricted local file or stdin (`--input -`); credential JSON is refused inline to avoid secrets in command arguments. Rotation uses `tm8 mcp credential rotate <credential-id> --input @credential.json` with only `secret`. Sharing and revocation use the explicit credential commands; connector visibility does not grant account use.

Attach an approved connector with the ordinary `equips` edge, directed from the task, teammate, or work session to the connector, with empty properties. Accounts are never attached to tasks. The graph cannot carry credential options on MCP equipment edges. A caller must be a member and must be able to access both endpoints in the same space. Unapproved and disabled connectors cannot be attached.

Worker and chat launch requests accept `mcpSelections: [{"serverId":"...","credentialId":"..."}]`. CLI launches use `--mcp-selections <json-source>`:

- Omitted selections resolve connector attachments on selected tasks, the teammate, and their accessible ancestors (at most 16 parent steps). The nearest attachment wins for a name; distinct definitions with the same name at the same depth are refused.
- `[]` disables all optional connectors.
- A nonempty array completely replaces attachment defaults.
- An authenticated connector always requires an explicit usable credential id. Missing or denied accounts fail readiness; the resolver does not choose another account.

`tm8 mcp resolve --input @selection.json` previews readiness. The request includes `spaceId`, optional `targetIds` and `teamMemberId`, and optional `mcpSelections`. `tm8 mcp server list --target <target-id>` exposes server-derived attachment permissions, including when the catalog is empty. New launches may use the selected teammate as their target before a task exists.

Connection test results are cached per testing member and definition version. Editing a definition invalidates its cached result. Another member does not inherit that account's tool inventory. Tools and cached status describe the last test; runtime authorization must still recheck the live session, selected account, approval, membership, and revocation before each use.

Security-relevant definition changes (URL, transport, authentication mode or metadata, header and environment slots, stdio command or arguments, private-network policy, or trust settings) advance the connector's security revision. Existing private credentials and pending OAuth consent are bound to the revision they authorized and fail closed until the owner reconnects. Display and provenance edits remain usable. Reverting a definition does not revive an invalidated credential. The update and credential-creation transactions serialize on the connector, and runtime checks compare the credential revision with the exact definition snapshot used for the request.

Development verification uses a fresh scratch database: `TM8_W1_ADMIN_DATABASE_URL=<scratch-postgres-url> node packages/server/node_modules/vitest/vitest.mjs run packages/server/test/db/mcp-foundation.pg.test.ts`. The suite exercises the full migration chain and generic entity round-trips. CLI checks are `bun run --cwd packages/cli test test/mcp.test.ts test/mcp-import.test.ts test/discovery-operations.test.ts`; the translator's own fixtures are `bun run --cwd packages/contract test test/mcp-import.test.ts`, and `packages/execution/test/mcp-import-toml.test.ts` cross-checks its Codex TOML reader against `@iarna/toml`.

OAuth requires an authorization server that supports PKCE S256 and suitable resource metadata. Discovery and dynamic client registration are attempted where supported; providers that require pre-registration need their own client id and approved redirect URI. A preregistered client may also be confidential: `auth.clientSecretEnv` names a server environment variable holding its secret, never the secret itself, and must match `TM8_MCP_CLIENT_SECRET_[A-Z0-9_]+` so that a definition cannot direct a token request at any other server variable. The token request authenticates with `client_secret_basic`, or with `client_secret_post` when that is all the issuer advertises. Starting authorization fails before the consent screen if the variable is unset. No provider account is bundled. The browser redirect is the public TM8 origin plus `/mcp/oauth/callback`: set `TM8_PUBLIC_ORIGIN` to the origin members open tm8 at, because without it the redirect is the loopback bind address, which a remote browser cannot reach. Only fixture protocol behavior is claimed here; live vendor compatibility requires provider-specific verification.

A sign-in that has begun but not finished is stored in Postgres (`internal.mcp_oauth_pending`, migration 342), not in server memory, so a restart between **Connect** and the provider's redirect no longer loses it, and two server instances can finish each other's sign-ins. Only a hash of `state` is stored; the PKCE verifier, the client and the token endpoint are sealed with the node key, and the row is consumed in a single `DELETE … RETURNING`, so a `state` is spent even when the provider then fails. A sign-in expires after 10 minutes; a node holds at most 1,000 live sign-ins and a person at most 20. When a sign-in fails at begin or callback, the error names its cause without echoing the provider's response: the provider offers no dynamic client registration, the provider refused registration (403, for example Figma's allowlist), the issuer did not match, PKCE S256 is unsupported, the redirect would be a loopback origin (set `TM8_PUBLIC_ORIGIN`), or the token exchange returned an HTTP status. Refresh and revoke keep opaque messages (ADR 0297).

## Catalog and connector requests

The connector catalog lives in `@tm8/contract` (`MCP_CATALOG`) and is read through `mcp.catalog.list` / `tm8 mcp catalog list`, which works without a Space and, given one, reports where each entry is already added or requested. It has six entries: Notion, Slack and Figma (relayed to the provider's own MCP server), and Gmail, Google Calendar and Google Drive, which tm8 serves itself (see below). Linear, GitHub and Atlassian are left out until a live check proves their dynamic client registration works.

A `catalogId` is an identity claim: the Connectors page draws a provider's name, logo and help from it. So the database holds its own copy of the catalog (`internal.mcp_catalog`, migration 345), and any definition naming a `catalogId`, an administrator's included, must carry that entry's exact URL and agree about `firstParty`. A drift test holds the SQL copy equal to `MCP_CATALOG`. A connector's name is unique among the Space's live connectors only, so deleting or withdrawing a connector frees its name.

Since 405 a member adds a connector directly and the UI no longer sends requests; the request door below remains for older clients. A member asks for a connector with `mcp.servers.request` (`tm8 mcp server request`). The request creates an unapproved `mcp_server` plus an approval request for the Space's admins. Nothing fetches its URL before approval: test and OAuth both check approval first. A catalog request names only the entry, and the server supplies the definition; an entry that is not available yet is refused. A custom request must be https and unapproved, and may carry no `catalogId`, `serverKey`, provenance, trust or reach flags, gates or client-secret variable. Each member can have 10 open requests and each Space 50. Asking again for a catalog entry returns the open request. An administrator who adds an entry that has an open request adopts that request by approving it with `mcp.servers.update`, which does not create a second connector. The requester can withdraw their own request while it is unapproved.

## Tool names the model sees

A connector's tools reach the model as `mcp__<serverKey>__<tool>`, for example `mcp__notion__search`, rather than `mcp__connector_<32 hex>__<tool>`. The key is the definition's `serverKey` or, absent one, its normalised name. It starts with a letter, uses lowercase letters and digits in segments joined by single underscores, is at most 32 characters, and is unique among the Space's live connectors under an advisory lock (migration 344). `tm8` is reserved for tm8's own bridge. The server computes keys at every launch and resume (`assignMcpServerKeys`), never from the request, so a renamed connector gets its new prefix at the next launch. Names that still collide at launch, such as pre-340 names that normalise alike, are resolved by ascending server id, so one set of connectors always yields one set of names.

## Changing a live chat's connectors

`chat.setMcpSelections` / `tm8 chat connectors <chat-id> --input <json>` changes a running thread's connectors. It takes three distinct values: `null` returns to the defaults, resolved fresh each turn; `[]` turns every connector off; a non-empty `[{serverId, credentialId?}]` replaces the selection. The write checks structure only (a live connector in this chat's Space, no duplicates). Approval and readiness are re-checked by compose and bind on every turn.

## Whose connections a session uses (provenance)

A connector call acts for one human, the provenance root, and is allowed only while that human is still a member of every Space in the chain (plan §6, migrations 343, 347, 348, 350, 351). The root is found from the spawning **bearer**, which is a server fact, never from the `launched_by` edge, which a caller can name. A human bearer (browser or CLI) is the root. An agent bearer hops to its own session's recorded binding. A loop firing is rooted at the member who armed the loop. The loop id reaches the spawn as a server fact, and the `triggered_by` edge is written in the spawn's own transaction, so a firing cannot exist without its root. A firing routed through a shared dispatcher is lent no account-bound connector. A `triggered_by` edge is provenance only when the spawn writer marked it so (`props.provenance`, migration 347). Any member can write run-history edges, and those lend nothing. A chain may not name a source that has no binding. The chain is recorded when the connection is bound and re-checked on every `tools/list` and `tools/call`. A launch with no provable human root is lent no connector that needs an account, and an agent bearer stays pinned to its own Space in every spaces mode.

## Per-call audit

Every connector call writes a `mcp_call_audit` row (migration 346), including calls refused before they reach the provider. A row records the tool name, the root member and chain, how the call arrived (`via`: `session` or `chat`), the chat, the credential and its scope, the outcome (`started`, `succeeded`, `failed`, `denied` or `refreshed`), a deny reason (for example `not_selected`, `root_not_member`, `root_left_chain_space`, `definition_changed`, `credential_required`), the latency, and the request and response sizes. Arguments and results are never stored. Provenance is copied from the binding, never re-derived. Only the audited session's own agent bearer can write its rows. If a row cannot be written, the write is retried once without the tool name and then logged; it never turns a call the provider already acted on into an error.

Read the log with `mcp.audit.list` / `tm8 mcp audit [--session <id>] [--chat <id>] [--connector <id>] [--member <id>] [--outcome <outcome>] [--limit n] [--cursor c]`. Reading is for people only. Space admins see every row in the Space; a member sees the calls where they are the root. Rows are kept for 90 days by default (`TM8_MCP_AUDIT_RETENTION_DAYS`, `0` keeps them), pruned in batches by the scheduler.

## Known limits

- A connector process or provider receives the credential it is configured with. tm8 controls who may call a connector and records every call, but it cannot constrain what a trusted stdio executable or a remote provider does with a valid token.
- Audit rows record that a call happened and its sizes, not its arguments, so they cannot answer *what* an email said.
- Connection tests (`mcp.servers.test`) do not yet write audit rows (follow-up in progress).
- External MCP tokens on `/mcp` (`tm8 mcp tokens`), the Settings → Connectors page and the composer connector toggles are documented with their own changes, not here. Refresh failures are below.

## Directory providers

Each member connects their own account; the directory only fills in the definition. Requirements come from each provider's official MCP documentation (checked 2026-10-19):

- **Notion** (`https://mcp.notion.com/mcp`, [docs](https://developers.notion.com/guides/mcp/get-started-with-mcp)): OAuth with dynamic client registration; no setup beyond approving the connector. Only workspace members can connect, not guests.
- **Slack** (`https://mcp.slack.com/mcp`, [docs](https://docs.slack.dev/ai/mcp-server/)): no dynamic client registration, and only internal or directory-published Slack apps may use MCP. Create a Slack app, enable MCP for it, add `<TM8_PUBLIC_ORIGIN>/mcp/oauth/callback` as a redirect URL and the user scopes, enter its Client ID in the connector, set `TM8_MCP_CLIENT_SECRET_SLACK` to its Client Secret in the server environment and restart. The issuer is pinned to `https://mcp.slack.com` because Slack's resource metadata names that origin rather than the `/mcp` URL. Slack's token endpoint labels the user token `token_type: "user"`; tm8 presents it as a bearer token, as Slack's MCP server's `WWW-Authenticate: Bearer` challenge asks.
- **Figma** (`https://mcp.figma.com/mcp`, [docs](https://developers.figma.com/docs/figma-mcp-server/remote-server-installation/)): only clients on Figma's MCP catalog allowlist can connect. Its registration endpoint refuses a client named `tm8` with 403, which Connect reports as "OAuth client registration rejected by provider". It works once the deployment is approved through Figma's MCP client waitlist.

Worker connectors support Claude Code and Codex bridge configuration. Chat retains the repository's existing Claude Code runtime; Codex chat is not supported by the baseline. Connector removal, account revocation, and account unsharing are separate actions. Revocation ends future account use; it does not delete the provider account itself.

## Google (first-party)

Gmail, Google Calendar and Google Drive have no provider-hosted MCP server, so tm8 serves them itself, in the server process (`packages/server/src/mcp/first-party/google/`). A definition with `firstParty: true` and a `google.*` `catalogId` is never relayed to its URL: the URL is the service's REST base and only identifies the connector, and the proxy calls the in-process host with the decrypted connection. Each connector reaches only its own Google API, whatever scopes the token carries. A connection records only its own connector's part of the Google grant, and gets only the tools its granted scopes cover: if the person unticks a scope at consent, the tools that need it are not offered, and a connection left with no usable tool is marked to reconnect (`scope_reduced`). Connect uses Google's static endpoints with `access_type=offline`, `prompt=consent` and `include_granted_scopes=true`; the node's Google client comes from `TM8_GOOGLE_OAUTH_CLIENT_ID` and `TM8_MCP_CLIENT_SECRET_GOOGLE` and is never stored in a connection. The connection's account label is the Google address from userinfo. Gmail is read + draft; `send_message` exists only while the connector's `gmailSend` gate is `true`. Disconnecting one Google connection deletes tm8's copy of its token but does not revoke at Google, because the account's Google connections share one grant; removing tm8 from the account entirely is done at <https://myaccount.google.com/permissions>. Setup and the live check: [docs/ops/GOOGLE-CONNECTORS-RUNBOOK.md](ops/GOOGLE-CONNECTORS-RUNBOOK.md).

## Refresh failures and revoke-all

When a provider refuses a connection's refresh token (`invalid_grant`), tm8 marks the connection **needs reconnect** and puts an inbox item in front of whoever can fix it: the member who owns it, or the Space admins for a Space connection. The mark is one-way; only reconnecting (OAuth) or rotating (API key) clears it. A refusal within 10 minutes of a refresh that worked is recorded as **possible token reuse** — someone else may hold the refresh token — and for a shared connection the Space admins are told too. This is a signal, not proof: Google rarely rotates refresh tokens, GitHub OAuth Apps have none, and Slack rotates only when the app opts in. A Google refresh that leaves the connector with no usable tool marks it to reconnect (`scope_reduced`); a partial grant stays active with the tools it covers. Every refreshed token leaves a `refreshed` row in the call audit. A network or provider error never marks a connection.

**Revoke all connections** (`mcp.credentials.revokeAll`, `tm8 mcp credential revoke-all --input <file>`) is the kill switch. Every connection in scope is revoked in tm8 first, so nothing can use it afterwards, and then revoked at the provider, best-effort:

- A **Space admin** (`{"spaceId": …}`) revokes every connection in the Space. Only Space-owned connections are revoked at the provider. Members' own connections are revoked in tm8 only: for Google, revoking at the provider would end the member's whole Google grant to tm8, including connections in other Spaces.
- The **node operator** (no `spaceId`) revokes every connection on the node, each at its provider, Google included. It needs `"confirm": "this signs tm8 out of every connected Google account"`.

Known limit: a backup taken before a disconnect still holds that connection's sealed token, and the key that opens it lives in the data directory. Keep backups and the data directory apart; see the operator guide, *Backups and restore*.
