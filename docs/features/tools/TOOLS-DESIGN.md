# Tools: design summary

The approved design is [doc 01a12587-b29f-74d5-8dd3-14a70051c2d1](tm8://entity/01a12587-b29f-74d5-8dd3-14a70051c2d1). Its resolved decisions (§8 and §9) define v1; the contract describes the implemented API.

A `tool` is a versioned bash or Python program with declared inputs and help. Humans and agents create and edit tools through `tools.*`. Each execution is a `work_session` with `sessionKind: tool`, linked to its definition by `executes`. Agent runs are children of their invoking session. Run history pins the definition version and source hash and records resolved public inputs, secret references, outcome, exit code and a redacted output tail (64 KiB).

Versioning rule (migration 388). Every write to a `tools` row appends its own `entity_versions` row and advances `entities.version` by one, in the same statement: the `tools_snapshot` trigger runs `internal.snapshot_entity_version('undebounced')`, opting the kind out of the generic five-minute same-author debounce that folded consecutive edits into one renumbered row. There is no second write path. A run pins `tool_version = tools.execution_version`, the stored version at which `source`, `runtime`, `inputs`, `tm8Access` or `timeoutSeconds` last changed, plus `tool_source_sha256`; `executionVersion` on the tool DTO is therefore "the version" the UI and CLI show, and `entity_versions(tool, tool_version).snapshot.content.definition` is the definition that ran. `entities.version` remains the optimistic-concurrency token: config and secret writes and name/description/help edits advance it and store a row, but none of them moves the pinned number. Row classification (the sentence UI and CLI quote, from BRIEF-TOOLS.md): a stored version is a definition version when `snapshot.content.execution_version` equals its own `version`; a metadata edit when its `content.definition` differs from the previous row but the execution version is unchanged; otherwise a configuration write, whose definition is identical to the previous row. Lists and diffs default to definition versions; `tm8 tool versions --all` and the UI's "all writes" toggle show the rest. Versions written before 388 may have been folded and cannot be recovered, and pre-388 runs pinned `entities.version`; readers resolve a missing row as "source unavailable" and keep the sha256.

Values resolve in this order: run arguments, configured values, declared defaults. Missing required inputs refuse the run. Inputs are validated against their declared type and arrive as environment variables. The source comes from the stored definition; the run request carries values. Environment names that could change the interpreter, PATH or tm8 identity are reserved.

Secrets can be supplied from an environment variable or bound to a sealed space credential. Binding/writing credentials is human-only; using one checks the invoker's credential visibility. Editing source preserves secret bindings, as approved. The source-change notice identifies changes since the viewer's last run. Live terminal output can contain secrets; persisted tails, events and command results redact them. Output redaction does not isolate the program from the node's filesystem or network.

The node materialises a private run directory and executes its generated wrapper through the work-session PTY. CLI/agent runs close on exit and propagate the tool's exit code. UI runs set `keepOpen: true`: completion is recorded while the PTY becomes an interactive shell with no idle auto-close. Before starting that shell, the wrapper removes all declared secret variables, `TM8_AGENT_TOKEN` and `TM8_SESSION_ID`. Closed runs kill background children in the tool process group. Timeout and explicit termination settle the run as stopped; ordinary exits settle it as completed, including a nonzero exit code.

`tm8Access: none` supplies no tm8 bearer and disables credential-store fallback. `read` and `write` mint a run-scoped agent token, capped by the caller's API scope and parent token lifetime. The facade rejects write operations under a read scope. Exit revokes the token; parent revocation cascades. An agent run's token acts as the invoking persona under its live bearer (`issue_tool_session_agent_session`, 319). A human CLI/UI run's token (`issue_tool_session_human_session`, 323) is a `cli` session for the human's own account, pinned to the tool's space and run, capped by the human's bearer scope and lifetime when one exists (the loopback owner has none), and revoked by the same settlement trigger.

The tool page (Tools v2) reads the run record back. `tools.runs.list` pages newest first (uuidv7 ids, `--cursor` continues with older runs); each run carries its `invoker` and, when a loop fired it, `triggeredBy: {id, title}` read only from the server-written, provenance-marked `triggered_by` edge (347), so a member-written edge cannot label a run as loop-fired. `tools.get`, `tools.list` items and the tool's entity summary carry `lastRun` (the newest readable run: session id, state, exit code, started and exited times) through one SQL fragment, so the header chip, the list tiles and the event projection cannot disagree. The version a page or a run prints is the execution version (388): the entity version at which what runs last changed; `version` stays the concurrency token. Versions are read from `entities.versions` and classified as `tm8 tool versions --format json` does: a row is a definition version when its `content.execution_version` equals its `version` (for rows stored before 388, when what runs differs from the next older row); other writes show under the version they run as. A run whose version has no stored row shows its pinned source hash, never an empty diff.

The starter set is [url-check](../../../examples/tools/url-check/), [gh-pr-status](../../../examples/tools/gh-pr-status/), [space-digest](../../../examples/tools/space-digest/) and [slack-notify](../../../examples/tools/slack-notify/). Each has separate source and a CLI spec JSON. The [integration suite](../../../packages/server/test/tools/tools-e2e.pg.test.ts) exercises the production server, throwaway database, real PTYs and CLI subprocesses with local external API stubs.

A loop can fire a tool with no HTTP request and no bearer: [SCHEDULED-RUNS.md](SCHEDULED-RUNS.md) is that seam (`ToolRuntime.runScheduled`, migration 389), the run's provenance-marked `triggered_by` edge and its kind-`agent` token acting as the loop's runs-as persona.

## v2: a first-class primitive

The v2 design is [doc 01a182cb-de75-7ec8-b8fe-650d4ca88580](tm8://entity/01a182cb-de75-7ec8-b8fe-650d4ca88580), "Tools v2: first-class primitive". It adds to the design of record without changing it: a UI create flow (New tab, Tools list, command palette) that starts from scratch or from a starter and sets the selection header; a tool page with a version history and source diff, a run-history table with an output drawer and a last-run chip, and the server's real error messages; the starter set as data in `@tm8/contract` (`TOOL_STARTERS`, generated from `examples/tools`, so the UI and the CLI offer the same four tools); CLI parity through `tm8 tool starters list|install`, `tm8 tool create --from-starter`, `tm8 tool versions` and `tm8 tool diff` ([TOOL-CLI.md](../../api-and-cli/TOOL-CLI.md)); agent discoverability (a prompt kernel line, a `tools` context-index group, MCP guide rows); and scheduled runs through a loop whose action is `tool`. Runtime decisions stated there and documented in [BRIEF-TOOLS.md](BRIEF-TOOLS.md): Python runs with the node's system `python3 -I` and site-packages (no virtualenv), a run that times out settles as `timed_out` with exit 124 or 137, eight live tool sessions per member, and a failed launch answers 503 `upstream_unavailable` with the run recorded as killed.
