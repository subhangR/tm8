07 · Inbox

Inbox, notifications, search, links and system states

The cross-cutting lane: the one list of what needs you, read across every server you are signed in to; the pushes that bring you back to it; search and entity chips, which move you between things; links arriving from outside the app; and the states every screen can fall into. New against the web phone shell: a native Inbox tab with fixed groups and swipe verbs, real push on both platforms (proposed — the node cannot send one yet), links that resolve across servers before anything renders, and an honest terminal state for a link to something you cannot see. That is cold-open defect N-1, which the web still has.

The Inbox — what needs you

The Inbox is the third tab. It is the web's T3-7 screen re-cut for a thumb. Two laws come over verbatim from inbox-model.ts, and one group is added on top. Groups render in a fixed order — Needs you · Mentions · Assignments · Delivery failures · Replies · Everything else — and nothing the viewer does reorders them. A read row fades; it never vanishes. Needs you is new: it is the attention queue's Personal roots, the decisions only you can settle. It sits above the news because a decision blocks someone and news does not.

Inbox root — Atelier, iOS lightThe anatomy phone. The fixed group order runs top to bottom, and Replies and Everything else continue below (see the Android phone). /[server]/[space]/(tabs)/inbox

The group order is the web's: an order the caller can vary will vary, so the native list hard-codes INBOX_GROUP_ORDER and only prepends Needs you. A notification tells you something happened. A Needs-you row asks you to decide, and leaves only when the request is resolved, never because it was read or seen. Mark all read therefore cannot empty the tab, and the badge keeps saying so. Undo for a bulk read is a held write rather than a reverse write, because the node has inbox.markRead and nothing that un-reads.

The four states of the list

The web keeps four distinct facts apart — "we haven't asked yet", "the read failed", "your filter hides everything", "your inbox really is empty" — because a viewer who cannot tell them apart cannot act on any of them. The phone keeps them apart too. Loading is the list skeleton in the system-states catalogue.

Row anatomy, per notification kind

One row grammar for every kind: headline (actor + verb, bold while unread) · target (kind glyph + title, or the attention chip on a Needs-you row) · an optional third line (the parent, per the tree ruling, or the quoted message) · time. NotificationItem.kind is an open union, so a kind this build does not know lands in Everything else with its name humanised (review_request → "requested your review"; an unknown foo_bar → "foo bar"). It is never dropped.

form asked · Needs you. An attention request raised by the chat that asked, pinned on the form and rolled up to its task. Tap: the asking chat at the form, chat/[id]?form=[id] (route proposed with lane 03; openTargetOf: an agent-raised request opens its source). Swipe: Pin · Resolve. Push: "Reviewer asked you: which tab bar?"

session waiting on you · Needs you. Raised by a work session (actionType approve · decide · unblock · review). PTY silence alone never makes this row. Tap: the session page with its waiting banner. Swipe: Pin · Resolve. Push: "Worker is waiting: push to origin", time-sensitive.

mention · Mentions. Third line: the quoted message, when the item carries one. Tap: the message on its anchor, highlighted (channel/[id]?msg=, or e/[id]/messages?msg=); this marks the row read. Swipe: Read · Pin. Push: "Priya mentioned you in #mobile".

assignment · Assignments. The target is a subtask, so the row names its parent (owner ruling 2026-10-28: a row for a child entity says "in ◆ parent"). Tap: the task page. Swipe: Read · Pin. Push: "Marco assigned you" · task title.

delivery failure · Delivery failures. A prepared reader: the contract has no failure kind yet, so the group renders only when rows like this arrive. Tap: the message on its anchor, where Send again lives — a new send with a new record, never "Retry". It cannot be offered on the row, which carries no message id.

reply · Replies. Tap: the thread on its anchor, at the reply. Swipe: Read · Pin. Push: grouped with mentions in the "Mentions and replies" channel.

review_request · Everything else. Tap: the PR page (lane 05). Its review state lives there, not on the row.

unblock · Everything else. Tap: the task. The row says who unblocked it; whether it is still blocked is the task's own pill, read when the task opens.

award · Everything else. The row shows only what the item carries: actor, target, message. It never invents a points figure.

stale · Everything else. With no actor the verb stands alone, capitalised. The kind tile replaces the avatar, because inventing "Someone" would put a fabricated fact on the loudest line of the row.

What “needs you” means — the attention model

“Needs you” is not a filter on notifications. It is the space's attention queue: requests raised on an entity (a form waiting for your answer, a session waiting on your permission, a decision, a review) and assigned to you, grouped by the root they roll up to. A request stays until someone resolves it. Reading or seeing it does not count, and PTY silence never raises one. The phone renders the same three surfaces as the web: the Inbox's Needs-you group, the Needs me filter on every list (the queue's mine roots for that kind, in queue order), and the attention control on each entity page.

Session waiting on you — iOS lightThe banner is the web's SessionWaitingBanner, labelled WAITING ON YOU. It sits between the head and the tabs, so it is the first thing under the title. Open terminal answers the prompt where it lives: the app never presses "Yes" on your behalf from a banner. Message writes to the session and the request stays open. Resolve… closes the request with an optional note sent to the session. The eyebrow is the parent chain (the chat that launched it). /[server]/[space]/session/[id]
Entity attention control, after a Resolve — Android darkTapping the attention chip on any entity page opens its requests, grouped by the root they count on, including the ones this entity's children raised. Resolve takes an optional note. The row dims in place, and the snackbar counts down the 8 s for which the node keeps a Resolve undoable (unresolve(batchId)). After that the sheet drops the row. The header chip is the same ! points · age as everywhere else. /[server]/[space]/e/[id]?sheet=attention
The Needs me filter, as a tree — iOS darkThe row source is the queue's mine roots for this kind, in queue order, never an intersection with the loaded page. Per the owner's tree ruling, a root that has a parent is drawn under it. The parent comes in dimmed, as context, with a count of how many of its children need you. The web draws this as one flat list; that is open question 1. /[server]/[space]/(tabs)/work?filter=needs-me
The banner never offers Approve. The permission prompt belongs to the agent's terminal, and the node has no verb that answers it on your behalf. A button that typed "1⏎" into a PTY would race whatever the agent printed next. The web ruling keeps Resolve separate from "answered" for the same reason: resolving a request settles the queue, and only the terminal settles the prompt.

Global search

Search is a modal, opened from the search icon at the top right of every tab root. The node's free-text search, search.query, is reserved and answers 501. The phone therefore searches what the node can answer today: collections.query with words (every word, matched across titles and short descriptions) and the kind, status and assignee filters. Message bodies and doc text are not searched. The screen says so instead of returning a silent nothing.

Opened, keyboard up — iOS lightFocus lands in the field. Recent queries and opened entities are kept per space on this phone. A hint chip inserts its token, and the tokens become collections.query filters: kind:, status:, @me → assignee, in: → subtree. /search (modal over any tab)
Results grouped by kind — iOS darkGroups follow the order of the Browse tab's kinds, and the filter chips count only the kinds present. Two matching subtasks come in under their parent, per the tree ruling. A doc row's excerpt is its short description, never a body match the node did not make. /search?q=tab%20bar
Query tokens, all servers, keyboard up — Android lightRecognised tokens echo as chips (tap one to remove it), so the query is legible without knowing the syntax. All servers runs the same collections.query on each signed-in server in parallel, and rows carry the server badge. /search?q=…&scope=all
Loading, then emptySkeleton rows hold the place while the first server answers. Empty says what was searched and where, and its verb widens the scope. A server still answering is named, never counted as "no results". /search?q=tabbar

Entity chips and links

A chip is the smallest unit of tm8: a kind glyph, the title, a state tint, and, for a reference into another space, a server / space badge. Tap pushes the entity's page. The web ruling stands: no peek on tap. Long-press opens a preview sheet. The same chip renders in prose, in markdown, in transcripts and in rows.

  1. Glyph + title. The kind glyph from the shared set; the title is ellipsised at 24 characters in rows and kept whole in prose.
  2. State tint. Working and live are green, waiting amber, blocked and failed red, in review blue. No tint means no live state. The word lives on the page, so the tint is never the only signal.
  3. Server / space badge. Only on a reference outside this space. Tap signs you in to that server first if needed (see the link flow).
  4. Snapshot. A dashed chip is a reference to the version the author linked (@v), labelled "as linked". The page opens on that version with "newer exists".
  5. Unavailable. The ref did not resolve for you: a lock and the short id, never a title the node did not send. Tap opens the terminal state below.
  6. In prose. Inline chips sit on the text baseline at 26pt and keep a 44pt hit area through padding.
Long-press a chip — Android lightThe preview is a card: the chip with its state as a word, the title, the parent chain, 2–4 summary fields chosen by kind, and a footer with the people and message count the node returned. A field that was not returned (points, cost) is left out, never shown as 0. Haptic: LONG_PRESS. iOS shows the same card as a context-menu preview. no route — a sheet over the current screen
A link to a message — iOS light…/channel/<id>?msg=<id> lands on the channel scrolled to that message, highlighted for 2 s with a brand rail, its thread one tap away. Opening it from the Inbox marks the row read. If the message was deleted, the channel opens at the end with a toast saying so. It never fails silently at the top. /[server]/[space]/channel/[id]?msg=[id]
Unavailable link — the N-1 fix — iOS darkOn the web, a cold link to an entity you cannot read opened a blank page with a spinner that never ended (nav matrix defect N-1). The phone resolves first and renders this terminal state: what was asked, where, what you can do. Its siblings use the same layout with the web's refusal copy: "You are not a member of this Space." · "This link’s Space is not on this tm8 node." Back goes to the kind's tab root. /[server]/[space]/e/[id] → unavailable
"Tap = push, long-press = preview" is the web chip ruling, kept: on a phone a peek-on-tap would turn the most common gesture into two taps. The unavailable state refuses to guess. EntityUnavailableRefusal gets one answer from the node for "deleted", "never existed" and "not yours", so the copy names all three rather than picking the comforting one. "Request access" is not offered because no such verb exists; the honest substitute is a link you can send to someone who can see it.

Deep and universal links

Every shareable address is a web URL on some server's host. The app claims each added server's host: iOS through Associated Domains (the node serves /.well-known/apple-app-site-association), Android through App Links (/.well-known/assetlinks.json, autoVerify). A self-hosted node the app was never told about cannot be claimed in advance. Its links open in the browser, which shows the "Open in tm8" banner, and the app then picks them up through the tm8://open?url= scheme. Serving both well-known files is a proposed node addition.

Resolving before rendering is the whole fix for N-1. The web mounted the entity page and let it discover, too late, that the read had failed. The phone treats a link as a request it can refuse. Cold-link back follows the Back Contract rather than the OS history: the person who tapped the link is now in tm8, and Back should keep them there.

System states — the catalogue

Each state is drawn once and used by every lane. A state names the server it is about, because with several servers signed in "offline" is a property of one server, not of the app.

Offline, queued writes, synced — v2Offline writes are v2 (lane 08); v1 shows the cached read and disables writes with the reason. Cached data stays readable under an amber banner that says from when. A write made offline shows pending on its row; Send now flushes the queue (the same records, not new sends). Only idempotent writes are queued (messages, read, status, carrying --expect-version). A queued write that comes back refused turns into the refusal card, never a silent drop.
Banners and the refusal cardUnreachable (red, per server) · node too old (info: the features it lacks are disabled with this reason) · app too old (amber: reads keep working, writes need the update) · rate-limited (with the node's Retry-After) · refusal (the node's code, its message, what was not changed, what to do).
Loading skeletonsThe list, page and transcript shapes. Shown after 150 ms, never for less than 300 ms, so a fast read does not flash. Cached data, when there is any, is shown instead of a skeleton.
Error boundaryOne per screen, not per app, so the tab bar still works. Report opens a prefilled message to the space's help channel with the stack and build. Nothing is sent without the tap.
Session expiredOnly the expired server asks; other servers keep working. "Later" leaves that server read-only from cache, with its banner.
Destructive confirm, then UndoThe confirm names the thing and everything that goes with it, including children per the tree ruling. Archive is tm8’s soft delete (entities.delete), the same word in every lane, and the toast that follows offers Undo through entities.restore. Undo appears only where a reverse verb exists; where none does (send a message) the app does not pretend.
Permission deniedCamera (QR sign-in, attach photo), microphone (voice), notifications (banner above): each names what it was for and offers the alternative that needs no permission.
