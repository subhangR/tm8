05 · Work

Work: tasks, lists and layouts, stories, projects, crafts, loops, pull requests

The Work tab is where a person sees what is moving and moves it: tasks grouped by status as a tree of subtasks, stories with the node's own rolled-up progress, and a board you page through with a thumb and drag across with a long-press. Under it sits one generic kind list, k/[slug], that serves every kind as a tree, list, board or timeline, and a page for each kind this lane owns. New against the web phone shell: hierarchy in every list (owner ruling 2026-10-28), a pager board, move and assign sheets that state the node's guards before you tap, and queued moves that survive a dead connection without pretending they landed.

The Work tab: Tasks, Stories, Board

Four segments; lane 04 draws Sessions. Tasks and Board read roots (parentId: null) and nest subtasks under them; a root is grouped by its own status, and each child keeps its own pill. Group counts are the server's CollectionGroup.total. When a node does not send one, the header says "3 shown" and gives no total.

Tasks and Board show roots because the Work tab answers "what is moving", and a subtask moves inside its parent. The full hierarchy is one tap away in k/tasks. Grouping by the root's status keeps the tree whole: a done child under a working parent stays where it belongs and shows its own "done". Timeline is not a Work segment. Recency is the sort, and on a 390pt screen a fifth segment would cost legible labels on the other four.
Category columns, not seven status columns, are the default because that is the web board-v2 rule: "a state the reads cannot isolate exactly downgrades the whole board to category columns", and tasks keyed on per-type workflows have more than one workflow. On a phone it also means four pages to swipe, not seven. Dropping a card on Done routes through complete, so the criteria gate is asked as it is on every other surface.

Any kind's list: k/[slug]

One screen for all 33 kinds, built from the kind's registry row: the plural label, the layouts it allows (hiddenModes), its sorts, its category tabs and its filters. The layout switcher offers tree · list · board · timeline. Tree is the default whenever any row has a parent of its own kind, and is decided from the data, not from kind names. A kind that hides a layout shows that icon disabled (commits: list and timeline only). The header count is Page.total when the node sends it; without one there is no number, never a 0.

Search runs within the list, and tree, list, board and timeline are one switch. Pushed from Browse, so Back says Browse. /[server]/[space]/k/tasks?layout=tree
Sort & filter (Android) over k/tasks in list layoutEvery option comes from the task row of the registry: eight sorts (the date, priority and progress sorts appear only because tasks have them), the category radio with "Not done" as the task default, the viewer chips, and the space's type axis (filters.axes). The task page

The overview's entity anatomy, filled in for the task. The order follows the routine a teammate runs (tm8 help routine): claim, keep the status true, tick as you go, link your work, finish. The page reads: header, verbs, liveness, description, acceptance criteria, blockers, children, git, sessions, then Messages and Linked, as on every kind.

  1. Back names where you came from (Work). The left-edge swipe does the same. A cold link lands here with Work underneath it.
  2. Share and ⋯: copy link, open on web, pin, copy id, link PR/commit, archive. Every one is disabled with its reason when capabilities says no.
  3. Kind eyebrow with short id, version and place ("root", or the parent chain for a subtask, see the states below), then the title, then status · priority (UPPER-CASE, as the tile badge spells it) · who has it · estimate · completion gate · opened by and when. Tap the pill to Move, the faces to Assign.
  4. The verbs. Launch opens lane 04's launch sheet. Chat opens lane 03's new chat with this task attached. Move opens the transition sheet. Assign opens the people sheet. Edit switches the page to edit in place: there is no edit dialog (owner ruling, form 01a1164f).
  5. Liveness appears only while sessions run here. View lists them (lane 04).
  6. Description is markdown, clamped to three lines. Tap to expand.
  7. Acceptance criteria. Tap a circle to tick: impactLight, and notificationSuccess when the last one lands. "Who · when" comes from doneBy/doneAt and is absent when the node does not send them. Ticks are version-guarded (task tick --expect-version).
  8. Add criterion is an inline field that writes the same version-guarded patch. Blockers, Children, Git and Sessions follow, then Messages and Linked (next two phones).
Lower half, a blocked task — darkBlockers come first: the status and when it changed, who it waits on (an approval_requested_from edge, so "waiting on Marco since Tue" is a fact, not a guess), and depends_on with resolved items struck. Children is a tree. Messages shows the latest few, and View all opens lane 03's thread. Linked groups by edge family (edge-families.ts) and leaves out what has its own section (depends_on, tracks). Provenance stays folded. /[server]/[space]/e/01a17e4c
Android: git and sessionsThe git section works like views/taskGitSection.tsx. The gate verdict comes before anyone taps Complete. Tracked PRs show lifecycle and CI (a null fact draws nothing). Commits name the session that made them (authored_from), and the worktree shows its state (active · merged · abandoned). Sessions lists live and exited sessions, each with its liveness word. /[server]/[space]/e/01a0e75e
Git is its own section, and Linked leaves out the Code family, so tracks is not drawn twice ("one fact, one place", as with remembers and triggered_by in the registry). Blockers comes above Children because blocked is the state the routine says to clear first. The PR's CI word comes from the observer's ciStatus. An older node sends none, so none is drawn, and it is never read as passing.

Move, assign, create

Three sheets. Each states the node's rule before the tap, in the node's own words (domain/workflows.ts: "the client narrows only for usability: the same rule, stated BEFORE the click"). The database stays the gate.

The transition sheetOpened from Inbox ("Subhang assigned you…"). The options follow the node's vocabulary, grouped by category. Pulled shows the workflow refusal in the words of workflowRefusalText. Complete is the only door to done and states the criteria gate as the server words it. "Claim it" is --claim: on by default only when you are an assignee, and it is never implied. Open and Cancelled say they end claims. /[server]/[space]/e/[id]/move (sheet)
Assign (Android, dark)Members are round, teammates rounded-square (provenance). Each tap writes or removes one assigned_to edge and applies at once. The node validates the pairing. Picking yourself offers "Assign & claim". The list scrolls to Dreamer, Graph Architect, Dispatcher, TM8 Helper and Fable 5.1 1M Teammate. /[server]/[space]/e/[id]/assign (sheet)
New task, keyboard upThe title is the one required field (createInstant: 'title'). Parent defaults to where you came from, so a subtask is born in its place. Criteria, estimate, assignees and the space's axes sit above the keyboard. Create is entity create task … --parent --criterion --estimate. /[server]/[space]/new/task?parent=01a182a2 (sheet)
The web's ruling that the transition list is "a vocabulary in reading order, not a state machine" is kept: every status is shown, and the only options disabled are the ones the node would refuse, with the reason. The claim is a separate switch, never a side effect, because the CLI keeps them separate: transition "changes only the status: the caller is recorded as working_on the task only with --claim". Move is not version-guarded on the node, so a stale page can still move. Tick, complete and edits are guarded, and a conflict is drawn below.

ProjectRepo and default branch come from projects.branches.list, with its source shown ("origin HEAD", not a guess). Files is the door to lane 06's file browser. Sessions launched here form a tree: the root session with its launched children, each with its own liveness word. The working folder shows only for node admins. Craft — ordered pages as a pagerEach page is the entity itself (graph, doc, artifact, drawing or another craft), held as an ordered contains edge. Swipe the body to page, or tap a thumbnail. Long-press a thumbnail to reorder: it lifts, and the drop writes collection add --position. "Launch all" (launch as one) runs one session anchored on the craft, with every page as context. /[server]/[space]/e/01a17c20?page=2

The run history is the triggered_by tasks: each firing derives one. /[server]/[space]/e/01a0e7d2

Pull requests and commits

What the forge observer stores is what the phone shows. Per-check rows (pr_check_facts) and review threads are stored on the node but are "not a client surface" today. Where this lane draws them, they are tagged proposed and need a read door.

PR #1113 — checks runningMerge… is disabled with its reason. Today the node refuses a merge only for not open, conflicts, failing checks or no GitHub credential. Holding the button while checks are pending is a client hold (see the open questions). Head is the observed head_sha, the commit this PR would merge. GitHub opens from the top bar. /[server]/[space]/e/[pr-id]
Merge… is two steps (Android)The confirm names the PR, the head and whose credential, in MergePullRequestFlow's words. A refusal shows above a disabled Confirm ("Merge refused — no GitHub credential stored for this account — connect one under Settings → Agent credentials"). Success shows the forge's sha and says the chip still reads open. Nothing repaints it locally. /[server]/[space]/e/[pr-id]/merge (sheet)

Moves that wait, refusals, conflicts

The states every write on these pages can land in. They are drawn on tasks, but they apply to every patch in the lane: story status, loop enable, collection add, craft reorder.

Offline: the move is queuedThe pill shows the asked-for status and "pending". Lists show the same pair. When the node accepts, the pending pill goes and a selection tick plays. If the node lands it elsewhere, the server's answer wins. Undo removes the queued write. /[server]/[space]/e/01a17a03
Refused, in the node's wordsComplete was tried from the board's Done column. The sentence is the database's (acceptance_criteria_incomplete, migration 151), and the open criterion is moved up beside a Tick. Haptic: notificationError / REJECT. /[server]/[space]/e/01a17a03
Version conflict, with the parent chainThe tick carried --expect-version 2. The node answered version_conflict with the current row, and the dialog names who changed what. Refresh re-reads and re-applies the tick only if the criterion still exists. Nothing is overwritten silently. Above the eyebrow is the subtask's parent chain. /[server]/[space]/e/01a182c6

Open questions for the owner 1. Pending checks. Should tracking.pr.merge refuse ci_status=pending (a new reason such as ci_pending)? Until it does, the phone's hold is client-only, and the web allows the merge.
2. Read doors. Per-check rows (pr_check_facts), review threads, and a single-commit diff are stored or reachable, but none is a client surface. Which of them should get a read door so the "proposed" tags can go?
3. Tones. The kit paints working and done the same green. The web desktop pill paints in_review amber and done grey, and the web phone row paints working blue. The meters here follow the story page (working blue). One ruling for all lanes would settle it.
4. Child caps. Children shown inline before "▸ N more": 2 on the Work tab and 4 in a kind list are proposed. Confirm or set one number.
5. Pause words. Loops say Disable/Enable, not pause/resume. Kept as the node's words. Confirm.
