03 · Chat

Chat: conversations, transcript, composer, channels, messages, forms

Chat is where tm8 work starts, so this is the screen the app is built around: a Chats tab of live conversations with teammates, a transcript that shows what each turn did to the graph (the receipt, one row per entity) instead of tool JSON, and a composer that feels native under a thumb — keyboard-docked, voice, paste, per-host / and @ pickers, an offline queue. What is new versus the web phone shell: native stacks and detented sheets, a live-turn row with Stop, a step sheet that holds tool cards one tap away from the reading flow, forms answered inline, chats that expand the sessions they launched, and channels and anchor messages that show delivery and record as two separate facts.

Truth this lane draws fromchat-home/turn-receipt.ts (one row per entity, marks made / moved / edited / linked / pending / failed), turn-steps.ts + turn-step-lines.ts (human step words, no tool names, R8), live-turn-status-model.ts (the now-sentence and clock), transcript/context-reading.ts (unknown is not zero), composer/composer-model.ts (roles over six modes, effort stops), ChatCredentialPicker.tsx, @tm8/contract chat.start and ChatWorkdirMode, rich-input/triggers.ts, channel-screen/feed-model.ts (delivery words), mobile/CONTRACT.md §3–§5, and tm8 help chat · message send · form. Where a screen needs something the node does not return today, the caption says proposed and the closing callout lists the server work.

Chats — the home tab

Newest activity first. Every row says what its conversation is doing in words: live pulses while a turn streams and the subtitle carries the live row's own sentence ("Worker · Writing…"), waiting means the agent is waiting on you (a form, a permission), exited means the chat's runtime is gone and the next message restarts it. A quiet row's subtitle is its last receipt as a sentence ("made 1 doc, linked PR #1012"). A chat that launched sessions carries them as a tree (owner ruling 2026-10-28 14:05).

The liveness words come from two server axes on the chat summary — the turn (streaming · idle · stopped-continuable · error) and the runtime (cold · live · stopped) — composed by one table (Components, below), never re-derived per screen; L7: "liveness never lies". The transcript — anatomy

The chat page is one screen: a header that names the conversation, the teammate and model, what it is about and whether it is live; the turns; the composer. Every turn below is drawn from the same parts the web transcript reads (thinking · text · tool_call · tool_result · usage · error · done), regrouped the way TurnParts.tsx regroups them: "the ledger, not the calls".

  1. Back names where you came from — ‹ Chats; the iOS edge swipe and Android predictive back both pop. The stack entry keeps this scroll position and the composer draft.
  2. Title, teammate · model — the chat's own title (rename from the menu) over the teammate and the model the next turn will claim. Tapping opens chat info.
  3. About chip and liveness word — the about edge as a chip (tap pushes the task); then the word: live · waiting · stopped · failed · exited · done. Never a bare dot.
  4. Context meter — used · percent of capacity from the chat's stored reading and live chat.context frames. "—" with a reason when nothing measured it; "last known" when the runtime is stopped. Tap for the detail sheet (used, capacity, remaining, cache reuse, sampled, model, source).
  5. Your turn — a bubble on the right, markdown, entity chips inline. Sidedness is by author id, not role.
  6. Agent byline — rounded-square avatar, name, model chip, time. A mode chip joins when the turn ran in a mode other than the chat's default.
  7. Thinking — collapsed to "Thought for 12s"; opens to the verbatim reasoning, never markdown. The duration is proposed (see Steps).
  8. Prose — the answer as markdown: headings, lists, code with Copy, tables, and every pasted entity id rendered as a chip.
  9. Steps — one header per turn: "12 steps · read 4 docs, ran 2 commands · 2 failed". Tap opens every run's list; a failure never folds away.
  10. Receipt — one row per entity the turn touched: the mark says what happened, the trailing word is the entity's state now, nesting shows a drawn edge, a refusal is a red row with the server's reason. Rows push the entity.
  11. Usage — the turn's own counts by the provider's categories; cost only when the runtime reported it.
  12. Composer — ＋ (add to this turn), the field, mic or Send; under it the picks row: mode, model · effort, credentials — each opens its sheet.

Live turns, third parties, failures

Live turn — Android, dark"New since you left" marks what arrived while you were away (this phone's own last-seen turn). The answer streams with a caret; the write in flight is a pending receipt row that the real row replaces in place; only the current run's steps are open. The live row says what is happening now, the clock and the silence ("last step 8s ago"; past 90 s it reads "still working", never an error) and owns Stop. The composer keeps Send: a message now queues behind the running turn. The pill appears when you scroll up and returns you to the live edge. /[server]/[space]/chat/[id]
Third parties, a failed turn, an interrupted turn — iOS, lightA session's report lands in the middle lane with "via ◆ Security lane A" — its persona is the same Worker summary the chat's own agent would carry, so only the authored_from source can say it came from elsewhere. Another human's turn sits left with a round avatar. A failed turn shows the runtime's message once, as the turn's own alert; a stopped turn pins the step it was in and freezes its clock. /[server]/[space]/chat/[id]
The live row is the only thing that narrates the present, which is why the transcript's step list is not a live region (web D15 §2) and why silence reads "Thinking…" rather than the last step in present tense: tools run in ~0.4 s and the model is then silent for 12 s on average (live-turn-status-model.ts, measured on the live node). Stop belongs to the row, not the Send button, because chat stop stops only the running turn — queued turns behind it still run — so the composer stays a composer. A stopped call is drawn stopped, not running: an interrupted runtime never writes a terminal record for the calls it abandoned, and a pulse on a call that will never finish is a lie.

Tool cards — the step sheet

Tool cards exist, but not in the reading flow. A step line is tappable; it opens the step sheet over the transcript, where each step can show its card: a shell command and its truncated output, a file read or edit as a diff excerpt, a graph write with its operation and the version it produced. The sheet is temporary and over your place (CONTRACT §4), so dismissing returns you to the paragraph you were reading.

Step sheet with tool cards — iOS, lightOpened by tapping a step line. A shell card shows the command, the first lines of output and "Show all"; a file card a diff excerpt; a graph-write card the operation, the new status and the version it produced. Strings shaped like credentials are masked (••••) before they render. Proposed amendment to R8, for this sheet only. sheet over /chat/[id] — no route (sheet content is never shared)
Kept from the web: no tool name, no box, no payload in the transcript (graph-seeds R8, pinned by no-tool-boxes.test.tsx; tool-call rules R1–R8, doc 01a0ddb5, signed off by Subhang). A turn that read nine entities once drew nine bordered cards each announcing tm8_read; the receipt and the counted step lines replaced them, and the phone keeps that. What the owner asked for — tool cards for the steps worth showing — lands where it cannot crowd reading: an explicit tap, a sheet, one step's card at a time. The explain_* cards stay inline exactly as on the web, because their payload is the content.

The composer

One composer component, three hosts — a chat, a channel, the messages on an anchor — each turning on the pickers its server path can honour: a chat gets / (skill references) and files; a channel and anchor messages also get @, because only messages.post carries mentions. Return inserts a newline on a phone (enterSends.ts); Send is the button. The keyboard inset is measured once at the frame and every bottom surface rides on it (CONTRACT §3) — natively, one KeyboardAvoidingView-class provider at the root, never a listener per screen.

The picks row is the web's split made physical: inside the composer is this message (mode, model · effort, ＋), behind ⚙ is this thread (credentials, where it works). The @ list is the CONTRACT §4 third shape — "a surface driven from an input it must not cover is not a sheet" — so it is never modal and never steals focus; the model and settings pickers are true sheets with their own focus and Android-back dismissal. Channels — feed, thread, voice

Channels live under the Chats tab (the overview's IA). A feed is people and agents posting, not a turn-by-turn conversation, so it reads like one: bylines over left-aligned posts, follow-on posts from the same author without a repeated byline, day separators, threads as a reply footer. Threads are replies, not children — the 14:05 tree ruling does not apply inside a channel.

Channel feed — iOS, lightHuman and agent posts by provenance shape, a mention highlighted, two image attachments, reactions in tm8's own three (like · dislike · star, counts from the post's counters; yours tinted), a thread footer with reply count, last reply and who replied, a voice-channel chip. Swipe a post right to reply in its thread. /[server]/[space]/channel/[id]
Thread — Android, darkThe root post, then its replies in order; the composer replies to the root (--reply-to). The bell follows or mutes the thread. A cold link to ?msg= opens here with ← returning to the channel feed, not out of the app. /[server]/[space]/channel/[id]?msg=01a17b9e

Messages on an anchor

Every entity can hold a discussion; a conversation is any anchor with messages on it. This screen lists every message on one task, doc or session, threaded, with reply and mention. Each message shows two facts, never one badge (tm8-ui law L7): the record — stored in the graph, or still queued on this phone — and the delivery to each live session on the anchor.

Every message on a task — Android, lightReplies indent under their root. The record facet and the delivery facet are separate pills. A message to several sessions summarises "7 of 8 delivered"; tap for the targets. "Send again" appears only on a retryable failure and posts a new message — there is no delivery-only retry. A failure never greys out the message: the stored thing is the fact. /[server]/[space]/e/[id]/messages
Message detail — iOS, lightA message is an entity: author, version, id, its anchor as a chip, the record facet, then delivery per target with the server's own reason for the one that failed. "Send again" re-posts to the failed target as a new message. /[server]/[space]/e/[messageId]
Delivery words are the web's, verbatim (feed-model.ts): stored · waiting to send, sending to session, delivered (the PTY write, nothing more), delivery failed · can send again, delivery failed, delivery unknown (a warning, never success), delivery expired, delivery cancelled. A message nobody attempted to deliver gets no delivery pill at all — "0 of 0" would state a measurement that never ran. The CLI agrees from the other side: message send --wait settled exiting 11 means stored-but-unsettled, not failed.

Model unavailable, effort undeclared — Android, lightOn an older node a chat's model can leave the catalog: Send is disabled and the refusal says why and what to do (chat model moves it). The context meter reads "— not measured" until a request reports usage. /[server]/[space]/chat/[id]
Offline is a state, not an error (principle 8). The cache is per server and per space; a queued message keeps the clientMutationId it was given on Send, so the server's idempotency makes a double post impossible when the queue drains. A queued turn is painted as an optimistic turn exactly as the web paints one before its ack (appendOptimisticTurn), with one more fact the web never needed: it may wait minutes, so it says so. Nothing here draws a count the node did not return — context "—", cost "not reported", unread absent.

Why the hero screen looks like thisThree web rulings carry over unchanged because they are about meaning: the ledger, not the calls (design ruling 1 and R8 — a turn says what happened to the graph, never which tools it called); one receipt row per entity (proposal 01a14a8d, approved by Subhang — made, moved, edited, linked, pending and failed folded into one row whose trailing word is the entity's state now); and honest states never collapse (L7). Two rulings are re-expressed natively: the owner's "opening an entity is always a full screen" stays (chips push), while the long-press preview the ruling left open becomes the iOS context-menu preview; the one-surface-at-a-time rule becomes stacks plus detented sheets, with the CONTRACT §4 third shape (a non-modal picker driven from the field) kept for / and @. One web behaviour is overturned: the phone shell had no tab bar and opened Chat as the drawer floor; here Chats is a tab root with its own stack, and the drawer's job moved to Browse (overview).
Open questions for the owner
  1. Tool cards. R8 (signed off) bans payloads in the transcript; this design keeps the ban inline and shows tool cards only in the step sheet on an explicit tap. Confirm the sheet may show the raw command and output (masked) — or should it show only the agent's own description, as the step line does?
  2. Per-chat unread (server). Widen loadUnreadCounts to chat anchors and write read_marks when a chat is opened; the primitive already groups over every anchor. Until then the dot, the Unread filter and "Mark as read" are absent.
  3. Chat pins. No server pin exists. Keep pins per device, or add a member preference so the desktop and phone agree?
  4. @ and entity references in a chat (server or convention). The chat wire carries no mentionIds. Proposed: write both as tm8:// links in the body, the convention / already uses, so no wire change is needed — or add mentionIds to chat send?
  5. Durations (server). Project message_parts.created_at on the transcript read so "Thought for 12s", per-step times and the step-header clock can be drawn for turns this phone did not watch live.
  6. Liveness word for an idle chat whose runtime exited. This design says exited (the runtime is gone; the next message restarts it). The web header says "not running". One word for both?
  7. Push for turn outcomes. Should a turn that finishes or fails while the app is backgrounded notify (lane 07), and only for chats you started?
  8. Voice presence. Participants come from LiveKit, not tm8. Acceptable that the room list can disagree with tm8 for a few seconds?
