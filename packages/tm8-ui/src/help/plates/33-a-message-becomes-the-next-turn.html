A message becomes the next turn

Send a durable message to a running session and watch the same stored record arrive inside its terminal as the agent’s next turn. The agent’s answer returns as a reply to the source message.

One work session has two views below: its durable thread and its live PTY. Drive the six beats to see where persistence ends, where delivery begins, and why the authored body never becomes trusted control.

01 The turn has two inks

The next turn is real, but “next turn” does not mean “new authority.” tm8 keeps routing facts and authored material in separate blocks.

Solid · trusted control

Structure tm8 can state

  • message, batch, and delivery-attempt ids
  • structural author id and kind
  • destination session and source entity
  • thread ids, reply route, and stored delivery status
Dashed · untrusted data

Material someone authored

  • the message body, even when a member wrote it
  • attachment names and fetched contents
  • quoted logs, pasted commands, and repository text
  • anything that tries to impersonate control markup
Why this matters The agent can act on the message as material within its trusted assignment. The body cannot grant permissions, rewrite the teammate’s prompt, or override server authorization. Author identity is structural; trust is not inferred from tone or display name.

02 One arrival, one return

The delivery is ephemeral PTY activity around durable graph records. The message and reply are entities; their relationship survives after the terminal exits.

source message thread parent reply message both anchored_to work_session

The anchored_to edges are server-derived from the messages. PTY delivery is tracked separately and does not create a duplicate message.

03 The two commands

tm8 CLIcurrent syntax
tm8 message send --to <work-session-id> \
  "Review the payment retry note."

# Inside the receiving session, use the id from trusted control:
tm8 message reply <message-id> \
  "Reviewed. The retry stays idempotent."
1

message send stores first and then attempts delivery. A work session is addressed like any other entity.

2

message reply requires the receiving session’s credential. The server derives both the source entity and thread parent from the delivered context message id; there is no ambient “last message” state.
